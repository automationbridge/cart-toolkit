Part 1

What to build

The big picture

Cart Toolkit handles the checkout. What happens after uses tools you already run.

The way to avoid bolting things on later is to keep Cart Toolkit's job small and clear. It owns everything up to and including the moment of purchase, plus handing your answers to Groundhogg. Access, tags and follow-up already have homes on the members site, and Cart Toolkit leaves them there.

Cart Toolkit

At checkout

  • Paid checkout forms: which options, which fields
  • Free signup forms: the $0 order
  • A read-only page showing today's SureCart setup, for the switch-over
Cart Toolkit

The hand-off

  • Every answer written to the order and to the member's Groundhogg contact, through WP Fusion as FC Toolkit already does
  • Fixed values a form sets, such as Membership Level = Free
  • A failed send is logged and can be resent
Tools you already have

After purchase

  • FluentCart's own FluentCommunity access (spaces, courses)
  • WP Fusion's FluentCart support: Groundhogg tags per product, order and subscription fields
  • Groundhogg flows, and FC Toolkit Access turning tags into spaces and courses
  • Anything OttoKit does today that none of these covers
WP Fusion added FluentCart support in version 3.47. The members site runs 3.48.2, so tagging buyers in Groundhogg per product probably needs no new code at all. It can't carry custom checkout answers, which is exactly the gap the hand-off fills. Mapping today's OttoKit steps onto this list is the next step, and it's why I need to see them (see What I need from you).
Modular by design

Five building blocks, each written once

Paid forms and free signups are two kinds of the same thing, so they share every block. A later feature, such as plan upgrades or licensing, becomes another page in the same admin and uses these blocks rather than rebuilding them.

Block 1

Field library

The fields a form can use, pulled from Groundhogg with their label, type and choices. You add a Groundhogg field to the library once, and from then on any form can use it. A field that isn't in Groundhogg can't be put on a form, so no answer is ever stranded.

Paid formsFree signup
Block 2

Forms

One list. Each form has a kind (paid checkout or free signup), a product, its options, fields picked from the library, a thank-you page and its own link.

Paid formsFree signup
Block 3

Form-only prices

Tick a price as form-only and it can only be bought through a form that includes it. Old or guessed buy links go to the form that sells it, and the server refuses it anywhere else. Current subscribers keep renewing.

Paid formsFree signupEvery FluentCart buy link
Block 4

Hand-off to Groundhogg

One sender. It takes an order's answers and fixed values and writes them to the contact. Both form kinds call it, and so would any later feature.

Paid formsFree signupLater features
Block 5

Shell: admin, logs, updates

The admin page, one log for everything, and GitHub updates. Same pattern as FC Toolkit, so it will feel familiar.

Walk-through

The two questions you asked about, in plain English

Form-only prices: decided, kept

A price marked form-only can be bought in one way only: through a Cart Toolkit form that includes it. Here's what a visitor sees at each door:

Where the visitor arrivesWhat happens with a form-only price
Your form's pageThe price is shown and can be bought, if that form includes it.
FluentCart's own product pageNot reachable. The product is set to Private in FluentCart, so its product page isn't public. FluentCart still allows its prices to be sold through forms and links.
An old or guessed buy linkSent to the form that sells that price. A link for a price that no form includes shows "This option is no longer available."
Anything that reaches the checkout some other wayRefused by the server before an order exists.
Someone already paying for itKeeps renewing as normal. Renewals never go through the checkout.

For Community Membership, all four prices are form-only. Scale and Growth are on the public form. Guest is on the free signup. Legacy is on no form, so nobody can buy it new, while current Legacy members keep renewing.

Question 5: an email that already has a login

You're right that it works like your current cart: name and email, then everything syncs. This question is about one case only.

Jane had a members-site login a year ago. Today she isn't logged in, and she signs up (or buys) with that same email. FluentCart makes her order but deliberately doesn't connect it to her existing login, in case the email was typed by someone else. Its FluentCommunity access still finds her by email and adds her. But when she later cancels or gets a refund, the removal only looks at connected logins, so her access would never be taken away.

The fix is for Cart Toolkit to connect the order to her existing login automatically, without logging anyone in. The only risk is that a stranger who types Jane's email gives Jane's own account access it didn't ask for. They gain nothing from that, because they still can't log in as her. This applies to paid forms as well as the free signup. My recommendation: connect it.

Server-side

What the server checks when the buyer clicks Place order

Run inside FluentCart's own validation step, before any order or charge exists. A failed check shows its message on the checkout, the way FluentCart shows its own errors.

1Is this cart tagged with a form, and does that form still exist and is it switched on?The tag is set by the server when the cart is made. The buyer can't edit it.
2Is every item in the cart one of this form's options?Otherwise: "That option isn't available on this form."
3Is any item a form-only price that this form doesn't include?Also covers carts made by FluentCart's own buy links, which belong to no form.
4Is every required field answered, and does each answer fit its type?An email field must be an email, a choice must be one of its options, and so on.

Feature 2

Free signup: a $0 order with no checkout page

The free signup is a second kind of form in the same Forms list. It uses the same field builder but has no options and no payment box. On submit, Cart Toolkit runs the same steps FluentCart's own checkout runs for a $0 order, so everything that follows a real purchase happens: the order, the customer, the WP user, the receipt email, your access feeds and the CRM.

From the source

Limits found in the source, and what the plan does about them

One checkout per page

FluentCart's checkout script can only run once on a page.

One checkout form per page. Free signup forms don't use that script, so one can sit beside a checkout form.

No option picker in free FluentCart

The checkout shows its items read-only. There is no filter on a product's option list.

Cart Toolkit draws its own picker and swaps the item on the server, using the same method as FluentCart's order bump.

The form page needs the cart in its address

The checkout script only sends a cart reference when the page address carries one.

The form's page redirects to itself with the cart added, the same way FluentCart's own buy links do.

No CRM custom fields in FluentCart's FluentCRM feed

Its custom field mapping is commented out, and no filter reaches the contact data.

Cart Toolkit writes the answers itself after payment, once FluentCart's feed has made the contact.

Products with attribute options

Products built with FluentCart's attribute options (size by colour and so on) take a different path.

The first build supports simple options, which is how your community product is set up. Attribute products come later, if needed.

Pro would also claim some settings

Pro uses variant_ids on the checkout shortcode.

Cart Toolkit uses its own names ([cart_toolkit_form]), so it never clashes if Pro is installed later.
